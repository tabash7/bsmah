قوائم تحقق تقنية

تجربة kiri بديلاً عن Docker Desktop: قائمة قبول قبل التشغيل في الفريق

قائمة قبول لتجربة kiri على أجهزة المطورين: التوافق مع Docker CLI وCompose، وخطوات التشغيل التجريبي، والتحقق الأمني، وكيف تقرر بعد التجربة.

الإجابة المختصرة

kiri أداة لتشغيل الحاويات تقدّم صفحتها على GitHub نفسها بوصفها بديلاً خفيفاً لـ Docker Desktop، وتذكر أنها تعمل مع أوامر Docker CLI وCompose. قبل اعتمادها في الفريق، شغّلها على عدد محدود من الأجهزة، واختبر أوامرك اليومية على مشروع حقيقي، وقِس النتائج بالمعايير نفسها التي تستخدمها للأداة الحالية، ثم اتخذ قراراً مكتوباً: نعتمد أو نؤجل أو نرفض.

يسمع مدير تقنية المعلومات أن فريق المطورين يجرب أداة جديدة لتشغيل الحاويات، ويقول أحد المطورين إنها قد تكون بديلاً لـ Docker Desktop. قبل السماح بتثبيتها على أجهزة العمل، يحتاج الفريق إلى سؤال واضح: هل تعمل أوامرنا اليومية كما هي، وهل يمكن التراجع بسهولة إذا لم تعمل؟

يشرح هذا المقال تجربة kiri بديل Docker Desktop خطوة بخطوة: تحديد نطاق التجربة، ومعايير القبول لكل نظام تشغيل، واختبار التوافق، والقياس، والمراجعة الأمنية، والوصول إلى قرار مكتوب. المعلومات هنا مستندة إلى صفحة المشروع ومستودعه، ويجب اختبارها بشكل مستقل على بيئتك قبل أي قرار.

ما نطاق التجربة، ومن يشارك فيها؟

قبل تثبيت kiri على أي جهاز، حدّد نطاق التجربة من حيث الأجهزة والأشخاص والمشاريع. تصف صفحة المشروع على GitHub kiri بأنه أداة حاويات خفيفة لأنظمة macOS وWindows وLinux، وأنها تعمل مع أوامر docker وCompose وbuildx. هذا الوصف مفيد للبداية، لكنه لا يغني عن اختبار يمثل عمل فريقك.

حصر النطاق يُبقي التجربة قابلة للمراجعة. إذا شملت كل الأجهزة والمشاريع من البداية، يصعب فصل المشكلات المتعلقة بالأداة عن المشكلات المتعلقة ببيئة كل جهاز. لذلك اختر مزيجاً صغيراً يغطي أنظمة التشغيل التي يعمل بها الفريق فعلاً.

ابدأ بجهاز أو جهازين لكل نظام تشغيل يستخدمه الفريق.

أي أجهزة تُدخل التجربة؟

سجّل نظام التشغيل وإصداره لكل جهاز قبل التثبيت. تذكر صفحة الإصدارات الرسمية ملفات التثبيت لأنظمة macOS وWindows وLinux، وتذكر صفحة المشروع أن macOS 14 أو أحدث مطلوب. على Windows يعمل kiri عبر WSL 2، ووفق وثائق Microsoft يلزم Windows 10 الإصدار 2004 أو أحدث، أو Windows 11.

الأجهزة الأقدم تحتاج خطوات تثبيت يدوية وفق وثائق Microsoft، لذا تحقق منها قبل موعد التجربة. يُنشئ kiri سياق Docker باسم kiri عند أول فتح، لذلك سجّل الأداة الحالية على كل جهاز، مثل Docker Desktop أو OrbStack.

من يملك قرار القبول؟

اجعل القرار بيد شخص واحد يتحمل مسؤوليته، ويراجع معه قائد الفريق التقني سير العمل اليومي. يسجّل المطوّرون ما ينجح وما يفشل في سيناريوهاتهم، ويراجع مدير تقنية المعلومات الأمن والصلاحيات قبل السماح بالتشغيل.

وضوح الأدوار يمنع أن تتحول ملاحظة فردية إلى قرار للفريق كله دون مراجعة.

ما معايير القبول لكل نظام تشغيل؟

تصف صفحة المشروع على GitHub أداة kiri بأنها تعمل على macOS وWindows وLinux، لكن شروط التثبيت تختلف بين هذه الأنظمة. لذلك لا يكفي أن تكتب في قائمة القبول «مقبول على كل الأجهزة». اكتب معياراً لكل نظام تشغيل، واربطه بإصدار محدد من الأداة.

يلخص الجدول أدناه ما تذكره المصادر، وما يحتاج فريقك إلى التحقق منه قبل القبول.

ماك وويندوز ولينكس: ما الذي يختلف؟

تذكر صفحة المشروع أن macOS يتطلب الإصدار 14 أو أحدث، مع معالج Apple silicon أو Intel. أما Windows فيعمل عبر WSL 2 على الإصدارين 10 و11، بمعمارية x86-64 أو Arm. وعلى Linux تذكر الصفحة توزيعات مثل Ubuntu وFedora، مع حزم .deb أو .rpm.

تختلف أيضاً أسماء ملفات التثبيت. تذكر README ملف .msi لويندوز، بينما تعرض صفحة الإصدارات للإصدار 0.1.14 ملف .msi لمعالج Arm وملف .msix لمعالج x86-64. لذلك اختر الملف من صفحة الإصدارات، وطابقه مع معالج الجهاز قبل التنزيل.

لا تفترض حدوداً دنيا للذاكرة أو المساحة أو المعالج. حدّد متطلبات الفريق من مشاريعه الفعلية، وسجّلها ضمن المعيار.

ماذا أسجل قبل التثبيت؟

على Windows، شغّل الأمر wsl.exe --list --verbose لعرض التوزيعات وإصدار WSL الخاص بكل واحدة منها. وتذكر وثيقة Microsoft أن التوزيعة التي تُثبَّت بالأمر wsl --install تُضبط على WSL 2 افتراضياً، ويمكن تحويل توزيعة موجودة بالأمر wsl --set-version مع اسمها والرقم 2.

سجّل أيضاً إصدار kiri واسم ملف التثبيت. تذكر ملاحظات الإصدار 0.1.14 أن خطوة Builds الاختيارية على Ubuntu كانت قد تفشل برسالة docker buildx create failed، وأن هذا الإصدار يعالج ذلك. إذا كان فريقك على إصدار أقدم، فأضف هذا البند إلى الفحص.

وإن أردت دليل تثبيت بالخطوات، فراجع أداة حاويات خفيفة بديل Docker: تثبيت kiri على ماك وويندوز ولينكس خطوة بخطوة.

  • سجّل نظام التشغيل وإصداره ونوع المعالج لكل جهاز.
  • سجّل إصدار WSL واسم التوزيعة على أجهزة Windows.
  • سجّل رقم إصدار kiri واسم ملف التثبيت المستخدم.

كيف أتحقق من توافق kiri مع أدوات Docker التي يستخدمها فريقي؟

يحتاج الفريق إلى أن تعمل أوامره اليومية، وليس صورة اختبار بسيطة فقط. اكتب قائمة بالأوامر التي يشغّلها المطورون فعلاً، ثم نفّذها على Kiri وسجّل النتيجة. بهذه الطريقة تعرف مدى توافق الحاويات في بيئتكم قبل أي قرار.

يذكر وصف المشروع على GitHub أن Kiri يعمل مع Docker CLI وDocker Compose وbuildx وdocker login. هذه ادعاءات يجب أن تختبرها بنفسك على الإصدار الذي تنوي تثبيته.

اكتب النتيجة المتوقعة لكل أمر قبل تشغيله، حتى تكون المقارنة واضحة.

أي أوامر أختبرها أولاً؟

ابدأ بالأبسط ثم انتقل إلى الأعقد. الفشل في أمر بسيط غالباً يشير إلى إعداد أساسي، بينما الفشل في بناء صورة قد يشير إلى اعتماد على ميزة محددة. هذا الترتيب يساعدك على عزل الفجوة بسرعة، والقائمة أدناه مرتبة بهذا الشكل.

افحص أيضاً أي محرك يستخدمه الأمر docker عندما لا تحدد سياقاً. تذكر ملاحظات الإصدار 0.1.14 أن Kiri ينشئ سياق kiri عند غيابه دون أن يغيّر المحرك الذي يستخدمه docker العادي. لذلك قد تظن أنك اختبرت Kiri بينما ذهب الأمر إلى محرك آخر.

  • تشغيل حاوية وإزالتها: docker --context kiri run --rm alpine echo hello
  • تشغيل مشروع Docker Compose: docker --context kiri compose up -d
  • سحب صورة من سجل الفريق بعد docker login
  • بناء صورة من Dockerfile الفعلي وتشغيلها

ماذا أفعل إذا فشل أمر؟

سجّل الأمر كاملاً، ونظام التشغيل، ونسخة Kiri، والمخرجات. ثم صنّف الفشل في واحدة من ثلاث فئات، لأن لكل فئة إجراءً مختلفاً:

  • إعداد: سبب الفشل خطوة تثبيت أو تهيئة لم تكتمل، مثل غياب سياق kiri أو عدم إكمال الإعداد الأول. الإجراء: أكمل الإعداد وأعد تنفيذ الأمر نفسه.
  • معروف: الفشل مذكور في ملاحظات الإصدار، مثل خطأ docker buildx create failed على Linux الذي تصفه ملاحظات الإصدار 0.1.14. الإجراء: تأكد من أن الإصدار الذي تثبته يتضمن المعالجة المذكورة.
  • مؤجل: الأمر يعتمد على ميزة لم تصل بعد، مثل البنّاء المدمج الذي يرد في خارطة الطريق. الإجراء: سجّله كفجوة مؤجلة مع موعد لمراجعتها، لا كفشل نهائي.

خطوات التحقق من أمر واحد

  1. 1

    حدّد الأمر

    اختر أمراً يستخدمه الفريق يومياً، واكتب نتيجته المتوقعة قبل التشغيل.

  2. 2

    شغّله على Kiri

    نفّذ الأمر بالسياق kiri، وسجّل الرمز الناتج والمخرجات كاملة.

  3. 3

    قارن وصنّف

    قارن المخرجات مع النتيجة المتوقعة، ثم صنّف الفرق وفق الفئات الثلاث أعلاه: إعداد، أو معروف، أو مؤجل.

ما خطوات التشغيل التجريبي على جهاز واحد؟

ابدأ بتشغيل تجريبي على جهاز واحد يشبه بيئة عمل المطور الفعلية، لا بجهاز اختبار نظيف. اختر مشروعاً حقيقياً وأوامر يومية معروفة، وسجّل حالة الجهاز قبل تثبيت kiri حتى تقارن لاحقاً.

الهدف أن تعرف هل تعمل أوامر فريقك كما هي، وهل يمكن التراجع بسهولة. هذه النتيجة تخص جهازك أنت، ولا تُستنتج من أرقام منشورة.

ما تدفق العمل من التثبيت إلى المراجعة؟

يعرض مسار التجربة المراحل الأربع بترتيبها. لا تنتقل إلى المرحلة التالية إذا فشلت الحالية، بل افهم السبب أولاً.

تقابل خطوات التجربة هذه المراحل: الخطوتان الأولى والثانية للتثبيت، والثالثة لإعداد السياق، والرابعة لتنفيذ الأوامر، والخامسة للمراجعة وتسجيل النتيجة.

كم مدة التجربة الأولى؟

لا تحدد المصادر مدة معيارية لتجربة kiri، لذلك لا نقترح رقماً. حدد المدة قبل البدء، واجعلها كافية لتنفيذ أوامر الفريق كاملة مرة واحدة على الأقل، مع وقت لمراجعة الأخطاء.

احسب أيضاً زمن التنزيل. وفق ملاحظات الإصدار في صفحة إصدارات kiri، لا يُنزَّل محرك البناء BuildKit عند الإعداد، بل عند أول عملية بناء، لذلك قد يظهر زمن التنزيل في أول بناء.

مثال توضيحي: فريق افتراضي في شركة لوجستية بجدة يختار مطوراً واحداً وجهازاً واحداً، ويعمل على مشروع فعلي، ثم يعرض النتائج على مدير التقنية قبل أي تثبيت إضافي.

خطوات التجربة

  1. 1

    تحقق من المتطلبات

    macOS 14 أو أحدث. Windows 10 بالإصدار 2004 وبناء 19041 أو أحدث، أو Windows 11، مع WSL 2. Linux عبر حزمة .deb أو .rpm.

  2. 2

    ثبّت kiri

    نزّل المثبت من صفحة الإصدارات في runkiri.com. تذكر الصفحة لنظام Windows ملفي .msi وmsix، فتحقق من النوع المناسب قبل التنزيل. إذا لم يكن WSL مثبتاً، فنفّذ wsl --install من PowerShell بصلاحية مسؤول، ثم أعد تشغيل الجهاز.

  3. 3

    تحقق من السياق

    بعد أول فتح لـ Kiri يُنشأ سياق Docker باسم kiri. تأكد من وجوده، ومن أن أوامر docker العادية لا تتغير إلا بقرار منك.

  4. 4

    شغّل أمر الاختبار

    نفّذ docker --context kiri run --rm alpine echo hello. ظهور الكلمة hello يعني أن المسار الأساسي يعمل، ولا يعني أن تطبيقات الفريق ستعمل. أكمل بأوامر الفريق نفسها.

  5. 5

    سجّل النتيجة

    احفظ الإخراج وأي خطأ في ملف مشترك للفريق، مع اسم الجهاز ونظام التشغيل وإصدار kiri ومدة كل خطوة. هذه السجلات أساس القياس قبل أي توسع.

كيف أقيس نتيجة التجربة قبل التوسع؟

القياس يحوّل الانطباع إلى قرار، فعبارة «بدت أسرع» لا تكفي. حدّد قبل التجربة مؤشرات قياس بسيطة، ومعايير القبول لكل مؤشر، ثم سجّل النتائج بالطريقة نفسها على الأداة الحالية وعلى kiri.

تنشر صفحة المشروع على GitHub أرقام أداء، وتذكر أن المنهجية وجميع الأرقام موجودة في الملف bench/results.json، وأن الأمر kiri bench يعيد التشغيل. هذه أرقام يقدّمها المشروع عن نفسه في README، وليست نتائج قياس مستقل. استخدمها لفهم ما يُقاس، لا بديلاً عن قياس فريقكم على أجهزته ومشاريعه.

أي مؤشرات أسجلها؟

اختر مؤشرات تربط نتائج التجربة بقرار واضح وقابل للعد. مؤشرات الحاويات المفيدة هنا عملية، مثل:

  • الزمن حتى أول تشغيل ناجح لمشروع الفريق من الصفر.
  • عدد أوامر docker التي تفشل خلال أسبوع العمل.
  • عدد الأعطال التي تحتاج تدخلاً يدوياً، ومدة إصلاحها.
  • الزمن حتى يستجيب أول أمر بعد فترة خمول.

كيف أقارن بالأداة الحالية؟

قارن المهمة نفسها على المشروع نفسه، وبعدد التكرارات نفسه. حدّد عدد التكرارات قبل البدء، واحسب الوسيط بدل الاعتماد على قراءة واحدة. هذا العدد قرار تضعه خطة الفريق، ويُعدَّل حسب حجم التجربة.

مثال توضيحي: يقيس فريق تطوير في شركة لوجستية بالرياض المهمة نفسها على الأداة الحالية وعلى kiri، ويسجّل الظروف في كل مرة. إذا تباعدت القراءات كثيراً، يزيد الفريق عدد التكرارات قبل أي حكم.

سجّل حالة الجهاز، وإصدار كل أداة، وعدد الحاويات المفتوحة. وإذا كانت لدى الفريق معايير قبول، مثل حد أقصى لعدد الأعطال، فاعتمدها قبل النتيجة لا بعدها.

قائمة مراجعة قبل التوسع

ما الذي أتحقق منه أمنياً قبل السماح بالتشغيل؟

قبل أن يشغّل المطورون حاويات من أداة جديدة، يحتاج فريق الأمن إلى مراجعة واضحة. أمان الحاويات يتطلب مراجعة التثبيت والتحديث والشبكة والصلاحيات معاً.

عامِل فحص الصور وتحليل الصلاحيات كأسئلة يجب إغلاقها مع فريق الأمن قبل التشغيل، لا كضمانات.

ما الذي تصفه الأداة عن التحديثات والتوقيع؟

تذكر صفحة المشروع أن kiri يحدّث نفسه، ويتحقق من توقيع كل إصدار جديد قبل تثبيته. اختبر سلوك التحديث داخلياً قبل الاعتماد عليه.

على Windows تذكر ملاحظات الإصدار أن كل تشغيل للمحرك يجلب نسخة هذا الإصدار، فلا يعود إصدار قديم مع كل تسجيل دخول. وعلى macOS وLinux تحذّر النافذة إذا ظهر kiri أقدم في PATH.

  • اختبر أن تحذير الإصدار الأقدم يظهر فعلاً على جهاز تجريبي.
  • راجع ملاحظات كل إصدار قبل ترقية أجهزة الفريق.

ما المخاطر التي أناقشها مع فريق الأمن؟

تشغّل kiri الحاويات داخل آلة افتراضية Linux صغيرة على macOS وWindows، وتعمل مباشرة على النواة في Linux. اسأل الفريق عن الفرق بين النموذجين، وعمّا تصل إليه الحاوية من ملفات الجهاز المضيف ومنافذه.

تستخدم الأداة نطاقات محلية بصيغة http://<name>.kiri.local مع HTTPS بشهادة من مرجع شهادات خاص بها. حدّد من يثبّت هذه الشهادة على الأجهزة، ومن يملك حق إزالتها.

الترخيص Apache-2.0، لكن اسم kiri وشعاره غير مشمولين به وفق README.

  • وثّق إعداد كل جهاز، وتأكد أن المحرك يبدأ عند الطلب لا مع كل تشغيل.
  • اتفق على طريقة الإبلاغ عن الثغرات، وابدأ من SECURITY.md الذي تشير إليه README.
  • اختبر إعادة تشغيل الجهاز، وتحقق من سلوك حاوية لها سياسة إعادة تشغيل.

تنبيهوصف التوقيع لا يغني عن مراجعة أمنية

وصف آلية التوقيع والتحديث مفيد، لكنه لا يغني عن مراجعة أمنية داخلية. اسأل عن فحص الصور وسجلات التدقيق وإدارة الصلاحيات، وتحقق منها في وثائق الإصدار المثبّت.

متى أنتقل من التجربة إلى قرار الاعتماد؟

تنتهي التجربة حين يستطيع الفريق أن يجيب عن سؤال واحد: نعتمد الأداة أم نؤجلها أم نرفضها؟ والمطلوب قرار مكتوب بسبب واضح. اجمع نتائج قائمة القبول ومؤشرات القياس وملاحظات فريق الأمن في وثيقة واحدة، ثم قارنها بالمعايير التي حددتها قبل البدء.

ويُستحسن أن تُجرى مراجعة ما بعد التجربة بعد فترة من الاستخدام الفعلي، لا في اليوم الأول فقط، لأن المشكلات المتكررة تظهر مع الاستخدام اليومي. وتذكر صفحة المشروع أرقاماً للأداء من قياساته الخاصة، لذلك يعتمد القرار على قياسات فريقك لا على تلك الأرقام.

ما الذي يكفي للاعتماد؟

يكفي الاعتماد حين تنجح أوامر الفريق اليومية على كل نظام تشغيل مستخدم فعلاً، وتبقى المؤشرات ضمن القيم التي حددتها مسبقاً، ويُغلق فريق الأمن ملاحظاته الجوهرية أو يقبل مخاطرها كتابياً. وإذا كان بين الأجهزة Windows، فالتثبيت يمر عبر WSL 2 وفق توثيق Microsoft، لذلك تُدرج خطوته ضمن خطة التثبيت.

  • نجاح قائمة أوامر الفريق على أنظمة التشغيل المستخدمة فعلاً.
  • مؤشرات ضمن القيم المقبولة المحددة قبل التجربة.
  • إغلاق ملاحظات الأمن أو قبول مخاطرها بقرار مكتوب.
  • خطة تحديث واضحة، مع التحقق من توقيع كل إصدار جديد كما يذكر المشروع. وإن كان الفريق سينقل من OrbStack أو Docker Desktop، فاختبر أمر kiri import على جهاز تجريبي أولاً.

متى أؤجل القرار؟

أؤجل القرار حين تكون النتائج مختلطة، أو يحتاج اختبار أمر محدد إلى وقت أطول، أو ينتظر فريق الأمن معلومة لم تُجمع بعد. التأجيل قرار سليم بشرط أن يُكتب سببه وموعد المراجعة التالية والشخص المسؤول عنه.

مثال توضيحي: شركة لوجستية افتراضية نجحت أوامرها اليومية على أجهزة macOS، لكن جهاز Windows واحداً لم يكتمل إعداده بسبب WSL. قرر الفريق التأجيل إلى مراجعة محددة، وكلّف شخصاً بإكمال الإعداد وتوثيق الخطوة.

أما الرفض فيكون حين يفشل شرط جوهري، مثل تعذّر تشغيل الأوامر الأساسية أو تعذّر تلبية متطلبات الأمن. ويُكتب السبب في جملة واحدة قابلة للمراجعة لاحقاً.

أسئلة شائعة

هل kiri بديل مجاني لـ Docker Desktop في كل الحالات؟

يذكر مستودع المشروع أنه مرخّص بترخيص Apache-2.0. لأي سؤال عن شروط الاستخدام في شركتك، راجع نص الترخيص في المستودع وصفحات الترخيص الرسمية للأدوات التي تستخدمها، أو استشر مختصاً قانونياً قبل قرار الاعتماد.

هل تعمل kiri على ويندوز مباشرة؟

تذكر صفحة المشروع أن Windows 10 وWindows 11 مدعومان عبر WSL 2، مع حزمة .msi من صفحة الإصدارات. لذلك اعتبر WSL 2 متطلباً في قائمة القبول، وتحقق من إصدار ويندوز على الأجهزة المستهدفة قبل بدء التجربة. ولا تفترض دعماً لأجهزة لا تستوفي هذا المتطلب.

هل تُغطي kiri أوامر Docker Compose وbuildx؟

تذكر صفحة المشروع أن kiri يعمل مع docker وCompose وbuildx، وتعرض أمثلة لأوامر مثل compose up. أما خارطة الطريق فتذكر أن البناء المدمج هو الخطوة التالية، لذلك اختبر سير عمل البناء لديك بنفسك. اكتب أوامر Compose وbuildx التي يستخدمها فريقك، وسجّل النتيجة لكل أمر.

هل يمكن تشغيل kiri في بيئة إنتاج داخل الشركة؟

لا يذكر README أن kiri معدّة لبيئة الإنتاج. تعرضه الصفحة بوصفه بديلاً لأدوات تشغيل الحاويات على أجهزة المطورين، مع ميزات مثل كلاستر Kubernetes بأمر واحد وآلات Linux. لذلك يحتاج أي قرار بالتشغيل في الإنتاج إلى مراجعة فريق الأمن والتشغيل، واختبار مستقل.

هل تقدم kiri نفقاً عاماً لعرض خدمة محلية على الإنترنت؟

ما يشرحه README بوضوح هو نطاقات محلية بصيغة kiri.local مع HTTPS من شهادة خاصة بـ kiri. وصف المستودع يشير إلى بديل لـ Ngrok، لذلك راجع وثيقة Features وملاحظات الإصدار للتأكد، ولا تعتمد على هذه الوظيفة قبل التحقق منها.

خطوة عملية

الخطوة التالية: قائمة قبول مكتوبة قبل التثبيت

اكتب قائمة قبول تغطي نظام التشغيل وإصداره، وأوامر Docker التي يستخدمها فريقك، ومؤشرات القياس، ومراجعة فريق الأمن، وموعد مراجعة ما بعد التجربة. ابدأ بجهاز واحد يشبه بيئة العمل الفعلية، ووسّع التجربة بعد مراجعة النتائج لا قبلها. إذا أردت مساعدة في تبنّي هذه الأداة، تواصل معنا.
